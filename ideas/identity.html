Identity: who is who

Once the mesh is open to other collectives, a bearer token and a shared secret aren't enough: anyone relaying a log could rewrite it. Every event needs a signature any node can check offline, and every key needs a reason to be believed. Almost all of that is a problem nostr has already solved, so kapwa's identity layer is nostr's.

What we take from nostr

neednostr already has
a signed eventNIP-01: id · pubkey · created_at · kind · tags · content · sig. The id is a sha256 over a tiny fixed array; the sig is Schnorr over the idIt canonicalizes, but the form is so narrow (strings, ints, arrays of strings) that dozens of stacks agree on it daily. The interop risk is already retired, and the test vectors already exist.
a collective's key, anchored to its domainNIP-05: /.well-known/nostr.json maps name@domain → pubkeyeveryday-vet@everyday.vet, sara@everyday.vet. TLS + DNS vouch the first time; nodes pin after. A changed key is loud.
who belongs to a collectivelists (NIP-51): a replaceable event signed by the collective's key, naming member pubkeysMembership is one event. Revoking is publishing it again without them. A person is a set of listed keys, so a lost passkey is a removal, not an identity death.
nodes proving who they areNIP-42: sign a challengeNo shared mesh secret.
a person's key from a passkeyNosskey: derives a nostr key from WebAuthn PRFExists, in the ecosystem we'd be joining. The RP-ID rule below still applies.
agents that shouldn't hold a person's keyNIP-46 remote signingA phone can be the signer for something that needs a human.
marks that evaporateNIP-40 expiration tagA claim that lapses on its own.
item idsan item is the event that created it; the rest point back with an e tagCollision-free ids from any writer, offline, for free.

A kapwa event as a nostr event

{
  "id": "4c1f…",
  "pubkey": "9f2c…",            ← sara's key, or her node's
  "created_at": 1789600346,
  "kind": 7410,                 ← a kapwa kind; ours to define
  "tags": [
    ["e", "a81b…"],             ← the item (its creating event)
    ["v", "take"],              ← the verb
    ["p", "5d30…", "to"],       ← dorkyrobot
    ["w", "everyday-vet/mini"], ← writer
    ["seq", "88"],              ← our completeness cursor
    ["ref", "kita:ev:d2877", "about"] ← a reference home
  ],
  "content": "taking it",
  "sig": "b7e0…"
}

Any nostr library can build, sign and verify this today. nak, the nostr CLI, can already debug our mesh.

What nostr doesn't have, and we keep

  • Completeness. nostr can't tell you "I have all of mini's events." Our per-writer seq rides along as a tag, and GET /api/log/<writer>?since= stays the sync. (NIP-77 negentropy exists if we outgrow it.)
  • Plain HTTP. nostr's wire is a websocket. We carry nostr events over our two GETs and a POST.
  • The fold, the board, collectives. nostr is the envelope, not the letter.

What it costs

  • secp256k1 Schnorr, not ed25519. PRF bytes work as either; microcontroller libraries exist for both.
  • Every event needs a signature, so raw curl can't author one. Hello-world survives because on localhost the node signs for its agents, the same stance as kitad stamping who.
  • created_at is whole seconds. Fold ties break on event id.
  • We don't join the public network. Our nodes are private relays.
One rule this brings: nodes never alter an event. Today kapwa parses lines and re-serializes them when relaying (key order already differs between the Elixir-written and Rust-written lines in your logs); that has to become store-and-serve verbatim. The same trap exists in kita: Act::id() is sha256(serde_json::to_string(self)), an id defined by one Rust serializer. Fine with one implementation; the first thing a second one trips on. Scuttlebutt signed JSON.stringify output, and it's a large part of why only one real implementation ever existed.

Who vouches for whom

What gets signed: three layers

layerwho signsanswerscost
0 · inside a machinenobody—Agents talk to their own node on 127.0.0.1 with a bearer key, as today. Same stance as kitad: authentication belongs in front of it.
1 · every eventthe writer (machine key, certified by its collective)"did everyday-vet really say this, and is this the line they wrote?"One signature per event, one verify on ingest. A relay can withhold; it can no longer forge or edit. The shared mesh token goes away; nodes identify with NIP-42.
2 · optional, the member signs insteadthe member (person or agent key)"did Sara herself decide this?"Only for acts that want personal non-repudiation — a decide, an approval. This is where a passkey-derived key earns its keep: Face ID to sign an order.

How does a person get a key? Three ways, side by side

A · Derived from a passkey (WebAuthn PRF)

navigator.credentials.get({ publicKey: { …,
  extensions: { prf: { eval: { first: "kapwa signing v1" } } } } })
→ 32 bytes → a nostr key   (Nosskey does exactly this)
  • The private key is stored nowhere; it's recomputed with Face ID / Touch ID
  • Synced passkeys give the same key on every device — Scuttlebutt's multi-device problem, gone
  • Same passkey + same salt → same key, forever
  • RP-ID scoping. Pocket ID's passkeys belong to id.felixflor.es. A page on kapwa-mini.felixflor.es cannot evaluate PRF on them, and Pocket ID doesn't hand PRF output to clients (nor should it)
  • So it needs a second passkey, registered by kapwa with RP ID felixflor.es (valid for every kapwa-* host). One extra enrollment per person per collective
  • The derived key is in page memory while signing — not hardware-bound. Use it to sign a short delegation, then drop it
  • Support: Safari 18+/iCloud Keychain ✓ · Chrome + Google Password Manager ✓ · security keys in Chrome ✓ · Firefox 139+ platform only · browser-only, so no CLI

B · Bound through Pocket ID, unchanged (OpenPubkey) lean, first

key   = new nostr keypair          # browser or CLI
nonce = sha256(pubkey ‖ random)
→ ordinary Pocket ID sign-in with that nonce
→ id_token, signed by id.felixflor.es, now says:
  "this key is felixflores@gmail.com"
  • Works today: our OIDC code already chooses the nonce. Pocket ID needs no change and sees a random-looking nonce
  • Uses the passkey people already enrolled
  • The collective's node verifies it once against Pocket ID's JWKS and adds the key to the collective's member list — so later verifiers never need the JWKS (rotation-proof)
  • Works from a CLI (device-code or loopback login)
  • The key itself lives somewhere: browser storage or a file
  • Trust roots in the IdP: whoever controls Pocket ID can mint members. True of every OIDC system, and it's your box

C · A key in a file

$ kapwa key new
pub npub1q9f…
# private half: ~/.config/kapwa/key, mode 0600

$ kapwa member add npub1q9f… \
    --name grok-cto --until 2027-01-01
# republishes the collective's member list
  • The only option for agents, machines, CI, an ESP32
  • Exactly the model you already run for SSH: generate, hand over the public half, get added
  • Someone has to vouch: a person with authority adds it to the list
My read. They aren't rivals. The protocol only says "nostr keys, and a member list." C for everything that isn't a person. B for people now, because it reuses Pocket ID untouched. A is an upgrade to where a person's key lives (nowhere), worth adding for layer-2 signatures once a second passkey enrollment is acceptable; A and B compose — a PRF-derived key can be the one bound through the nonce.

One thing I'd rule out

Serving a kapwa page under id.felixflor.es to reach the existing passkey

A cloudflared path rule could route id.felixflor.es/kapwa/* to kapwa, which would make PRF on the Pocket ID passkey work. It also means kapwa's JavaScript runs with the identity provider's origin — its cookies, its session. A bug in a dashboard becomes a compromise of sign-in for everything. Not worth it.

What this does for the earlier worries

worrywith signatures
"Managing API keys" for external usersThey generate a key; you add it to the list. authorized_keys, but replicated and revocable.
The injection channel between agentsby becomes provable, so a reader can weigh a note by who provably wrote it and which collective vouches for them — rather than by what the note claims.
A relay rewriting historyCan't: every event verifies against its author. It can still withhold; peers comparing seq notice. (A prev hash per line would make truncation and equivocation provable too — later, if needed.)
The shared mesh tokenGone. Nodes prove who they are by signing a challenge (NIP-42); there is no shared secret to leak.
