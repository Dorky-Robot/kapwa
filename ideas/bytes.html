Moving bytes

Files and live streams, directly between the people and machines in the mesh: you and Doug today, a practice and its clients tomorrow. This is a third concern, so it is a third tool, not a feature of kapwa. kita knows. kapwa owes. A mover moves. Each does one thing well, and each is useful without the others.

The third thing

kita — what we know

Holds the record: the scan, the recording, the contract, as content with an identity. Never sends it anywhere.

kapwa — what we owe

Carries the reference and the commitment: "I'm sending you this", "got it", "delivered on the 14th". Never carries the bytes. That was already the rule: bytes don't travel.

the mover — how bytes and streams travel its own tool

Built on iroh: dial a key, not an address. Direct, encrypted QUIC between two devices, hole-punched through NAT, relayed only when it must be. Rust-native, 1.0 since June 2026. Working name below: hatid ("to deliver to its destination"). Yours to name.

The mover doesn't need kapwa at all: a ticket can be pasted into any chat. It uses kapwa only when it wants what kapwa is good at — a durable, signed, addressed record that something was offered and received.

Why a separate tool

What separation buys

  • Focus. kapwa is a ledger of commitments. Long-lived connections, NAT traversal, relays and throughput are a different job with different failure modes.
  • Weight. kapwa stays small enough for a shell script or a microcontroller to implement. iroh's dependencies live elsewhere.
  • Pace. Real-time networking moves fast; a ledger format should barely move at all. Separate tools version separately.
  • Surface. A process that listens for inbound QUIC and serves files from disk has a very different security profile from one that appends signed lines.
  • Choice. Because kapwa only points at bytes, other movers stay possible: a plain HTTPS link, a USB stick, whatever comes next.

The seam: three things, again

IdentityThe same nostr key says who you are in both. The collective's member list binds a key to "dial me at iroh:…".
A payload["payload","hatid/offer","…"]: a type kapwa has never heard of, and a string it never opens. Nothing about the mover appears in kapwa's spec.
ReceiptsThe mover reports offers and deliveries by saying them on kapwa, with source:"hatid", through the same CLI or HTTP any agent uses. No private hooks.

What it costs

  • One more thing to install and run where bytes move (not everywhere).
  • Version skew across a seam; kept small by keeping the seam to a tag.
  • Both tools need the key. A shared convention (one key file, or a NIP-46 signer), not a fourth daemon.

The same test sorts features into the three: is it about what we know, what we owe, or what we move? Calls, screen sharing and presence are "move".

What it looks like

Between two nodes

$ hatid send site-plan.pdf --to doug \
    "the revised plan"
serving 14.2 MB · said 9c41e on kapwa

# on Doug's machine, in prime or on the board:
asked of you (1)
  9c41e  from felix · site-plan.pdf 14.2 MB
         "the revised plan"

$ hatid take 9c41e
fetching · direct · 38 MB/s · verified ✓
saved ~/Downloads/site-plan.pdf
# …and says so on kapwa: done 9c41e "received, verified"

The mover is just another agent using kapwa's public interface: it says the offer and says the receipt. kapwa gains no verbs, no code and no dependency. The ledger still ends up with what a practice needs: who was offered what, who fetched it, when, and that it arrived intact.

The event underneath

{
  "kind": 7410,
  "tags": [
    ["v", "say"],
    ["p", "…doug…", "to"],
    ["payload", "hatid/offer", "{…}"],
    ["expiration", "1790200000"]
  ],
  "content": "site-plan.pdf, 14.2 MB: the revised plan"
}
# hatid/offer — the mover's business, opaque to kapwa
{ "name": "site-plan.pdf", "size": 14200000,
  "blake3": "bafk…", "ticket": "…" }

kapwa neither reads nor stores the file, and doesn't know what an offer is. It sees a sentence, an addressee, and a payload of a type it has never heard of. An expired ticket is a dead link, by design.

A practice and its clients

Why it's a game changer

  • The record never sits on anyone else's server. Not a portal, not an inbox, not a file-sharing site.
  • Nothing to install, no account for the client. A link in a text.
  • Proof of delivery lands in the practice's ledger, and from there in its kita: "sent Bella's x-rays to her owner; fetched the 14th, verified."
  • It expires. A ticket is a capability, not a permanent URL.
  • With a client app later, the same link becomes fully direct and fast. Nothing else changes.

Caveats, honestly

  • The practice's node is the server. It must be on. (The mini is; a laptop isn't.)
  • Relayed means relay-speed. n0's public relays are free, rate-limited, and meant for development. Real use wants our own.
  • A relay needs a publicly reachable port, including UDP for address discovery. That is the one piece that doesn't fit "everything behind a cloudflared tunnel": a small VPS, or a forwarded port.
  • Big files in a phone browser are bounded by memory and patience.
  • What may be sent, to whom, with what consent is the application's policy, exactly as with parcels. The signature makes it accountable; it doesn't make it allowed.

How it fits what's already decided

Two kinds of key: iroh dials ed25519 node ids; nostr identities are secp256k1Different jobs. The nostr key is who you are; the iroh id is where to dial. The collective's signed member list (or its well-known file) says "reach dorkyrobot/mini at iroh:…", the way nostr relay lists say where someone writes.
"A lightweight Rust binary"kapwa stays 5 MB and dependency-light, because none of this is in it. The mover is its own small Rust binary that carries iroh's weight, installed only where bytes need to move.
"A transport a shell script can't speak must never be the only one"kapwa speaks only HTTP, permanently. (n0 does publish ESP32 examples, so small devices aren't shut out of moving bytes forever.)

The laptop comes off its flapping tunnel without kapwa changing at all.

The ten-minute spike

sendme is n0's own file-transfer tool, built on exactly these pieces. Two runs, on your own machines only:

  1. mac2024 ↔ the mini, same network. Proves the path and gives a throughput ceiling.
  2. mac2024 tethered to your phone ↔ the mini at home. A real NAT on one side and a carrier's on the other, which is the hardest case there is. This one tells us whether it hole-punches or falls back to a relay, and at what speed.
# sender
$ sendme send ./big.bin
# → prints a ticket

# receiver
$ sendme receive <ticket>

If it's direct and fast, kapwa send is a thin layer over a proven path. If it relays, a self-hosted relay is step one.
