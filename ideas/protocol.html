The protocol

Three ideas: every writer owns one log, replication is a pull by sequence number, and the board is a deterministic fold over all logs. The whole wire contract fits on an index card, and the vocabulary you need on day one is four verbs.

The whole protocol on an index card

This is the test: if it doesn't fit, it isn't the protocol, it's a convention.

KAPWA  v1

event   {"kind": "...", "id": "...", ...anything you like}
        the node adds:  writer  seq  at  by

write   POST /api/event
        Authorization: Bearer <your key>
read    GET  /api/board.txt
        Authorization: Bearer <your key>
sync    GET  /api/log/<writer>?since=<seq>
        Authorization: Bearer <mesh token>

rules   append-only.  the key is your name.
        unknown kinds and fields are kept, and ignored.

This is v1, exactly what the four nodes run. With signing, the event becomes a nostr event and the three routes stay as they are.

That already exists and already works. Hello world is two lines, no SDK, no install:

curl localhost:3410/api/event \
  -H "Authorization: Bearer $KEY" \
  -d '{"kind":"note","id":"hello","note":"hi from a shell"}'

curl localhost:3410/api/board.txt \
  -H "Authorization: Bearer $KEY"

Day one: four verbs

What you type

$ kapwa say "A2P profile is stuck on ISV"          # makes an item
said 7f3c2

$ kapwa                                            # the board
$ kapwa take 7f3c2                              # I've got it
$ kapwa say 7f3c2 "support case 29429182 open"  # a note on it
$ kapwa ask 7f3c2 "Direct or ISV? only you know" # pulls the cord
$ kapwa done 7f3c2 "reclassed"
$ kapwa drop 7f3c2                              # changed my mind

No flags needed. No id needed to start. Forgiving like JS: sloppy input makes something reasonable rather than an error.

2 · Replication is a pull by seq

3 · The board is a fold

Order

All events from all logs sorted by (at, writer, seq), then applied one by one. Every node runs the same fold on the same events and gets the same board. at first is what makes "earliest claim wins" mean the same thing everywhere; writer then seq break ties deterministically.

kindeffect
createnew item; a second create for the id is a note
claimowner = by if unowned or already by; else recorded as lost
releaseowner = "" if owner == by

assign / resolveowner = to / status = done
notehistory only
unknownkept in the log, ignored by the fold — a newer node can write what an older one skips

Topics, not channels

Right now everything is everything: one board, and every node sees all of it. "Channels" is the obvious fix, and it bundles four different problems into one heavy concept. Pulled apart, each already has a small answer, and none of them is a channel.

what a channel is asked to dowhat does it herenew concept?
Attention: "I only care about the roof"A topic tag on the item, ["t","roof"], and a filter when you read. A saved filter is your "channel" (kita calls it a scope)no: tags were always allowed
Audience: "this is for the practice"Address a participant. A collective is already a participant, so --to everyday-vet reaches everyone in it; a team is a smaller listno
Visibility: "others must not see this"Decision Y1: a node serves an event only to its author's collective and to those it is addressed to. A topic never grants or denies accessno
A place to talk: "the ops room"A long-lived item. Everything said about an item already hangs off it, in order. An item that stays open is a roomno

What it looks like D21

$ kapwa say "Roof leaks over the back door" \
    --t roof --t urgent
said 2m8q1

$ kapwa --t roof            # the board, filtered
$ kapwa prime --t roof,fence # an agent that only works those

# a standing place to talk is just an item you never close
$ kapwa say --as ops "standing: ops chatter"
$ kapwa say ops "tunnel on the laptop flapped again"

An agent's key can list the topics it cares about, so prime is scoped without anyone typing flags. Default scope, with no topics at all, is already narrow: what's addressed to you, what you hold, what's asked of you.

Why not real channels

  • A channel is a folder. Each message lives in exactly one, and someone has to choose which. kita exists to refuse that: a thing belongs in many places, and "two people never chose the same keywords." An item can carry five topics; it can only sit in one channel.
  • Channels weld topic to access. A private channel is a subject and a permission in one object, which is why they need membership, invites, admins and archiving. Keep them apart and each stays trivial.
  • nostr has no channels in its core either: events carry tags, readers subscribe with filters. Group chat exists there only as optional conventions on top.
  • It would be the first container in kapwa. Everything so far is marks plus folds.
The one real limit: topics narrow what you read, not what a node stores. Sync is per-writer and contiguous, which is what makes "I have all of mini's events" provable, so a node can't skip the lines it finds boring. That's fine while logs are kilobytes. A device too small to mirror doesn't sync at all: it asks a node for a filtered board. If logs ever get large, the answer is a writer per area of work, not filtered replication.

Riders: what kapwa carries without knowing

kapwa is an envelope and a ledger: who said what to whom, about which item, in what order, signed. It is deliberately ignorant of everything else, including kita. Other protocols ride it the way attachments ride email: SMTP has never known what a PDF is.

Two generic slots, no named siblings

["ref", "kita:monica:d310", "about"]
# a reference: some URI, and optionally a word for
# how this item relates to it. kapwa knows no schemes.

["payload", "kita/act", "…"]
["payload", "hatid/offer", "…"]
# one opaque string, with a type. kapwa stores it,
# signs it, delivers it, and never opens it.

Neither is new: both are already covered by the card's last line, "unknown kinds and fields are kept, and ignored." This just names the convention so riders agree on where to put things.

The rules that keep it honest

  • Every event still reads as a sentence. content is for people and agents; a payload is for the rider. The board makes sense with no rider installed.
  • A rider is just an agent. It uses the same verbs through the same CLI and HTTP. No plugins, no hooks, no registration.
  • A rider never depends on kapwa. kita works alone; the mover works alone. They use kapwa when they want a durable, signed, addressed record.
  • Payloads are small (a cap, say 64 KB). Anything larger is bytes, and bytes are the mover's job.
  • Opaque cuts both ways: kapwa can't screen what it can't read. What may leave a collective is the rider's and its application's responsibility, with a signature attached.

Scaling: it never needed a full mesh

Today every node pulls every other node every 5 seconds. That is N×(N−1) edges, and it's a configuration, not a property of the protocol. Because every node serves the logs it has mirrored, replication works over any connected graph: Doug's mini already peers with only two of your three machines and still has mac2019's log. The question is only which graph.

The principle from day one still holds: the data model is the protocol; the transport is swappable. Per-writer logs, signed events and pull-by-cursor work over HTTP, and HTTP can itself be carried over anything. kapwa never needs to know what is underneath, and a shell script or an ESP32 can always speak it.

Every device is a node: laptops, phones, browsers

A true peer network has no servers, only peers that happen to be reachable more or less often. That is exactly what the design already assumes: every writer owns its own log, writes while offline, and catches up later. "Hub" is a property — always on, reachable — not a role. The protocol treats a phone and the mini identically; topology is just who can be reached right now.

kind of nodeexamplescan be pulled from?how its log gets out

comes and goes, unreachablea phone, a browser tab, an ESP32 on someone's Wi-Fi, a laptop in a caféno — nothing can connect init publishes its own log to any reachable peer, and pulls everything else as usual

Sync is two-way over one outbound connection built

Pull can't reach a phone. So whoever opens the connection does both halves: it pulls what it lacks, then hands over what the other side lacks.

GET  /api/writers            # what do you have?
GET  /api/log/<w>?since=N    # give me what I lack
POST /api/log/<w>  [lines]   # here is what you lack
→ {"wrote": 2, "have": 412}
  • One rule both ways: only the next seq is written; on a gap the receiver answers what it haves and the sender resumes there. Idempotent; safe to retry forever.
  • Any reachable node will do. No primary, nothing to fail over.
  • Trust today is the mesh token, the same trust a pull already extends. Once events are signed it becomes per-author: a peer can store your events but never forge them, so it stops mattering who delivered them.
  • This is nostr's shape: clients publish to a relay. It's why the laptops need no hostname.

The phone, concretely

A · An installable web app lean

  • Nothing from an app store; add to home screen
  • The key lives nowhere: derived from a passkey with Face ID (WebAuthn PRF). This is where that idea fits best
  • Own log in the browser's storage; pull and publish over plain HTTPS; works offline
  • Web Push for an ask addressed to you (decision Y2), which iOS allows for installed web apps
  • Files over iroh in the browser: relayed, still end-to-end encrypted
  • It is the dashboard that writes, and it's the second implementation of the protocol, in TypeScript — the proof that this is a protocol
  • Can't listen, so it's always the "publishes its own log" kind
  • Syncs when open or woken by a push, not continuously

B · A native app around the Rust core

  • Direct iroh connections: fast file transfer, local discovery without internet
  • The same code as every other node
  • An app to build, sign and ship
  • iOS suspends background apps: it still can't be an always-on peer
  • Worth it when phone-to-phone transfers or streaming matter; not before

One address, then peer to peer

What's true today running

kapwa.felixflor.es is the mesh's only address. It points at the mini, which has no peers configured. mac2024 and mac2019 have no hostnames; they reach out. It's also the collective's public face: one address for other collectives, one sign-in callback for people.

This is how the grown-up meshes do it: Tailscale's coordination server and relays, Syncthing's discovery server, BitTorrent and IPFS bootstrap nodes, a nostr relay URL. One stable rendezvous; it doubles as the relay of last resort.

What "peer to peer thereafter" means, honestly

  • Today the gateway relays. It stores and forwards every log, so two laptops converge through it. That is robust and simple, and it isn't direct.
  • Direct connections need NAT traversal, and that is the mover's job, not kapwa's: it can hand kapwa a local port that is really another node, dialed by key over iroh. kapwa keeps speaking plain HTTP and never knows.
  • The gateway then shrinks to discovery (who is in the mesh, how to dial them) plus fallback. Lose it and nodes that already know each other keep syncing.
  • More than one gateway is cheap: any always-on node can answer the same name, since every node mirrors everything.

What makes it a protocol, not an app

The spec is small and frozen at the bottom

Nostr: NIP-01 is the protocol, everything else is optional. Ours: the index card is KIP-01; verbs, signatures, collectives, the kita pointer are KIP-02…05. A conforming implementation needs only KIP-01.

Bytes are defined, not objects

A line is its UTF-8 bytes. Ids and signatures are over those bytes. Implementations store and forward lines verbatim. For signed events we take nostr's NIP-01 id and signature rather than invent one: its canonical form is narrow enough that many stacks already agree on it (details).

Test vectors are the contract the important one

A directory of JSON files any implementation runs:

vectors/
  fold/     events in → board out
            contested claim · unknown kind · orphan note
  ingest/   lines in → what gets stored
            gap · replay · foreign writer · torn line
  sig/      line + key + sig → valid?
            tampered byte · wrong key · expired cert
  cert/     chain → trusted?
            revoked · expired · unknown root

Scuttlebutt had one implementation and no vectors; "the protocol" was whatever that code did. Vectors are what make the Rust node a reference rather than the definition.

Unknown is kept, and ignored

Old nodes relay what new nodes write. No version negotiation, ever. Already true for both: kita's open vocabulary, kapwa's open kinds.

What keeps it easy

View source

The log is a text file: tail -f ~/.kapwa/log/mini.jsonl. The board is plain text. You can debug the whole system with cat, grep, curl.

No build step

No SDK, no schema registry, no OAuth dance, no registration. A key in a file. A second implementation is an afternoon — that's the bar Nostr set and Scuttlebutt missed.

Forgiving

Extra fields are kept. Unknown kinds pass through. Old nodes relay what new nodes write. Nothing ever needs a version negotiation.

One name

One binary, kapwa: kapwa serve is the node, everything else is the client. Not kapwa + a CLI + an MCP server.

Copy-pasteable

The index card is what kapwa --help prints first and what GET / returns to a curl. An agent that lands cold learns it in 120 tokens.

Progressive

Layer 2 exists for whoever needs it. Nobody is made to learn it, and no client breaks for not knowing it.

Honest limits today. The fold re-reads every event on every write — fine at this scale, incremental folding when it isn't. Claims are eventually consistent (above). Keys are a file per node; minting as events is queued. Reads are not yet product-scoped.
